# Localization (i18n) — how it works, and how to change it

This is the reference for the site's translation system: what it is, how to
add a language, how to add a translatable string when building a new
feature, and the mistakes that are easy to make here specifically. Written
for a human maintaining this repo AND for an LLM (Claude Code or otherwise)
picking up a task in this area cold — every instruction below names the
exact file to open.

## The shape of the system, in one paragraph

One CSV (`src/locales/translations.csv`) is the single source of truth for
every translated string, edited directly by Arko or a developer. A build
script (`scripts/i18n/build-locales.mjs`) turns it into one JSON resource
file per language under `src/locales/generated/` (git-ignored — a build
artifact, regenerated by `predev`/`prebuild`/`pretest` in `package.json` and
by CI). `react-i18next` serves those resources to components via `t()`.
English is the **unprefixed, default** locale (`/`, `/order`, `/about`, ...);
every other language gets a URL prefix (`/de`, `/de/order`, ...) via a
parallel route tree under `src/routes/$locale/`. Both route trees render the
**same page components** from `src/pages/`, so there is exactly one copy of
each page's JSX/logic — only the strings it pulls from `t()` differ.

The admin panel (`src/routes/admin/**`), `/orders`, and `/reset-password`
are **deliberately not localized** — Arko's instruction was that the admin
panel stays English-only, and those two customer routes are account/session
utility screens, not marketing content. Don't add translation keys for them
unless that decision changes.

## File map

| File / directory | Role |
|---|---|
| `src/locales/translations.csv` | **The file you edit.** Wide CSV: one row per key, one column per language (`key,en,de,...`). |
| `scripts/i18n/build-locales.mjs` | Converts the CSV into `src/locales/generated/{locale}.json`. Validates: every key needs a non-empty English cell (hard error), warns (doesn't fail) on a blank non-English cell. Run via `npm run i18n:build`; also runs automatically before `dev`/`build`/`test` and in CI. |
| `src/locales/generated/*.json` | Build output. **Git-ignored — never hand-edit.** Regenerate with `bun run i18n:build`. |
| `src/lib/i18n.ts` | i18next init, `SUPPORTED_LOCALES`, `DEFAULT_LOCALE`, RTL list, `localizePath()`. The list of languages the site ships lives here. |
| `src/lib/seo.ts` | `canonical()`, `localeLinks()` (hreflang tags), `pageHead()` — builds a page's whole `head()` return value from its `seo.<page>.*` keys. |
| `src/pages/*.tsx` | The actual page JSX, shared by the English and translated routes. **This is where you add `t()` calls when building a feature.** |
| `src/routes/*.tsx` | Thin English route wrappers (`index.tsx`, `about.tsx`, `history.tsx`, `order.tsx`, `subscribe.tsx`, `privacy.tsx`) — each just wires a page component to `pageHead(path, DEFAULT_LOCALE, "seo.xxx")`. |
| `src/routes/$locale/_layout.tsx` | Pathless layout matching `/de`, `/de/about`, etc. 404s any locale not in `SUPPORTED_LOCALES`. |
| `src/routes/$locale/_layout.*.tsx` | Thin translated-route wrappers, one per page, dot-chained off `_layout` (same convention as `src/routes/admin/_layout.*.tsx` — a static `admin/` directory there vs. a dynamic `$locale/` directory here). |
| `src/components/layout/LocaleLink.tsx` | `LocaleLink` / `LocaleButtonLink` — wrap TanStack's `Link`/`ButtonLink` and prefix `to` with the current locale. **Use these for every internal link**, never the raw `Link`/`ButtonLink`, or a German visitor gets bounced back to English on click. |
| `src/components/layout/LanguageSwitcher.tsx` | The EN/DE control in the header — links to the *same page* in each other language. |
| `scripts/build-static.mjs` | Prerenders the static export. Its `ROUTES` array has an explicit locale × path list near the bottom (currently `["de"].flatMap(...)`) — **this is not automatic**, a new language or a new translated page needs an entry here too. |
| `.github/workflows/deploy-frontend.yml` | CI's "Build translations" step runs `scripts/i18n/build-locales.mjs` before typecheck, so a broken CSV fails the deploy loudly. |

## Recipe: add a new language

Say you're adding Arabic (`ar`, RTL):

1. **Add a column to `src/locales/translations.csv`.** Every existing row
   gets an `ar` cell. You don't have to fill in every translation on day
   one — a blank cell falls back to English at runtime and the build script
   just warns about it (see "How the build script behaves" below). English
   itself must never be blank for any row.
2. **Register the locale in `src/lib/i18n.ts`:**
   - Add `"ar"` to `SUPPORTED_LOCALES`.
   - If it's RTL, add `"ar"` to the `RTL_LOCALES` set.
   - Add `import ar from "@/locales/generated/ar.json";` and add
     `ar: { translation: ar }` to the `resources` object passed to
     `i18next.init()`. (Resources are bundled statically, not fetched at
     runtime — see the comment above that call for why: this is a fully
     static site with no server to fetch a locale bundle from at request
     time.)
3. **Add it to the static build's route list.** In
   `scripts/build-static.mjs`, add `"ar"` to the locales array in the
   `["de"].flatMap((locale) => ...)` line near the end of `ROUTES`.
4. **Font/script support, if needed.** Cormorant Garamond + DM Sans (loaded
   in `src/routes/__root.tsx`'s `head().links`) are Latin-only. A script
   they don't cover (Arabic, Bengali, ...) needs a paired font added to that
   same Google Fonts `<link>` — this is a manual design decision (which Noto
   family, whether to load it only for that locale to avoid paying its
   weight on every other page), not something this system does for you.
   Flag it to Arko/design before writing code.
5. **Rebuild and look at it for real:**
   ```bash
   bun run i18n:build   # regenerates src/locales/generated/*.json, catches CSV errors
   bunx tsc --noEmit
   bun run dev          # visit /ar, click the language switcher into and out of it
   bun run build:static # confirms /ar/... prerenders; check dist-static/ar/index.html
   ```
   **Don't skip the live browser check.** Typecheck/lint/tests do not catch
   layout breakage from a longer or RTL string, and they would not have
   caught the language-leaking-across-pages bug described below — that one
   was only visible by actually clicking around.
6. Fill in the rest of the CSV column over time; each save + `i18n:build`
   (or just restarting `dev`, which reruns it automatically) picks up the
   new text immediately.

## Recipe: add a new translatable string (building a feature on an existing page)

1. **Pick a key** following the existing dot-namespace convention:
   `<page>.<section>.<field>`, e.g. `order.giftNote.label`. Look at
   neighboring keys in `translations.csv` for the page you're touching to
   match its naming style.
2. **Add one row to `translations.csv`** with the English text and a
   translation for every language column that already exists. If a value
   needs a runtime variable, use `{{name}}` interpolation syntax (i18next
   default) — see `order.decrease` (`"Decrease {{name}}"`) for a working
   example, called as `t("order.decrease", { name: item.name })`.
   - A CSV cell that itself needs a comma or a literal `"` : wrap the whole
     field in `"..."` and double any internal `"` (`""`) — standard CSV
     quoting, not backslash-escaping (the parser is `csv-parse`, which
     doesn't support `\"`).
   - A few keys store a short delimited list rather than one sentence (e.g.
     `product.kacchi.tags`, joined with `|`) — split it in code with
     `.split("|")`. Only use this for genuinely list-shaped data, not as a
     way to avoid adding more rows.
3. **Consume it** in the relevant `src/pages/*.tsx` component:
   ```tsx
   const { t } = useTranslation();
   // ...
   <span>{t("order.giftNote.label")}</span>
   ```
4. **Never hardcode customer-facing English text directly in JSX.**
   Anything a visitor reads — labels, placeholders, `aria-label`s, error
   messages — goes through a CSV key. The one standing exception is the
   admin panel (see above) and any literal brand name / proper noun that's
   identical in every language (e.g. "Dhaka Kacchi", "WhatsApp").
5. Run `bun run i18n:build` (or just restart `bun run dev`, which runs it
   via the `predev` hook) to see the new key immediately.

## Recipe: add a brand-new page

1. Write the page as a shared component in `src/pages/NewPage.tsx`, using
   `useTranslation()` throughout — copy the shape of an existing page like
   `src/pages/SubscribePage.tsx` (simple) or `src/pages/AboutPage.tsx`
   (multiple sections).
2. Add its SEO keys to the CSV: `seo.newPage.title`, `.description`,
   `.ogTitle`, `.ogDescription`.
3. Add the English route, `src/routes/new-page.tsx`:
   ```tsx
   import { createFileRoute } from "@tanstack/react-router";
   import { NewPage } from "@/pages/NewPage";
   import { DEFAULT_LOCALE } from "@/lib/i18n";
   import { pageHead } from "@/lib/seo";

   export const Route = createFileRoute("/new-page")({
     head: () => pageHead("/new-page", DEFAULT_LOCALE, "seo.newPage"),
     component: NewPage,
   });
   ```
4. Add the translated route(s), one file per shipped locale, following
   `src/routes/$locale/_layout.about.tsx`'s pattern exactly (same idea, new
   path segment):
   ```tsx
   import { createFileRoute } from "@tanstack/react-router";
   import { NewPage } from "@/pages/NewPage";
   import type { Locale } from "@/lib/i18n";
   import { pageHead } from "@/lib/seo";

   export const Route = createFileRoute("/$locale/_layout/new-page")({
     head: ({ params }) => pageHead("/new-page", params.locale as Locale, "seo.newPage"),
     component: NewPage,
   });
   ```
5. Add `"/new-page"` to **both** places in `scripts/build-static.mjs`'s
   `ROUTES`: the plain English list, and inside the locale `flatMap` so
   `/de/new-page` also gets prerendered. If it shouldn't be indexed by
   Google, also add it to `isExcludedFromSitemap()`.
6. Any internal link on the new page uses `LocaleLink`/`LocaleButtonLink`,
   never the raw TanStack `Link`/`ButtonLink`.
7. Run the full verification checklist below.

## Rules that exist because something already broke

- **Never call `i18n.changeLanguage()` anywhere except the one place it
  already happens** — `syncLocale()` in `src/routes/__root.tsx`, called
  from `RootShell` off the router's real `useLocation()`. i18next is a
  single shared instance across the whole app. It used to be synced from
  the root route's `beforeLoad`, which seemed right (runs before render, on
  the server and on every client navigation) — except `beforeLoad` **also**
  fires when the router speculatively preloads a route on link hover, with
  no real navigation happening. That meant hovering the language switcher
  on the English homepage silently re-rendered the *entire page* in German
  while the URL stayed on `/`. `useLocation()` only ever reflects the
  router's actual, committed location, never a preload, which is why the
  fix reads locale from there instead. If you're tempted to add a second
  place that changes the language (a new layout route, a "remember my
  language" effect, anything), route it through `syncLocale()` or you will
  likely reintroduce this.
- **`head()` functions must use `pageHead()` / `i18n.getFixedT(locale)`,
  never the reactive `t()` from `useTranslation()`.** `head()` isn't a React
  component — it has no hooks — and more importantly it needs to describe
  *that specific route's own* locale (from the URL/params it's defining),
  not whatever the shared i18next instance's current language happens to
  be at the moment it runs.
- **Every internal navigation goes through `LocaleLink`/`LocaleButtonLink`.**
  A plain `Link to="/order"` on a German page sends the visitor back to the
  English order page.

## Verification checklist

Run all of these after any change in this area — they catch different
things, and the last one is not optional:

```bash
bun run i18n:build     # CSV parses, no missing English cells
bunx tsc --noEmit
bun run lint
bun run test
bun run build:static   # prerenders every locale; spot-check dist-static/de/.../index.html
bun run dev            # then actually click around: switch languages on a few
                        # pages, check nothing overflows with longer German text
```
